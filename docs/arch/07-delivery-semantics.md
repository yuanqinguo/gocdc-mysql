# 07 · 投递语义与幂等设计

> 投递语义的明确承诺：at-least-once + 幂等收敛，把「崩溃重放」变成安全操作而非数据事故。语义写进 README 与监控口径，不许含糊。

## 1. 语义承诺（写进 README 与监控口径，不许含糊）

| 承诺 | 内容 |
|------|------|
| 管线内部 | 位点永不超前于已投递数据 → 重启/切主只可能**重复**，不可能**丢失** |
| MySQL sink | **幂等、最终一致**：同一事件重放任意次，目标表终态不变；表内有序 |
| Kafka/RocketMQ | **at-least-once，可能重复，不丢**（进程内无丢弃路径；位点到 etcd 的持久化是异步节流的，crash 窗口重放） |
| 跨 sink（双写） | 各自独立 at-least-once；位点推进要求全部启用 sink 确认 |
| 不承诺 | 恰好一次（exactly-once）、跨表事务原子性、跨 sink 原子性——下游以 `event_id` 幂等消费实现等效 |

## 2. 事件唯一标识与下游去重

- `event_id`（05 §2.1）：file:pos:row_index（GTID 模式 gtid:seq），全局唯一且稳定——同一事件重放生成相同 id。
- 消费方幂等模式（文档提供示例）：
  - 直接落库：按 `event_id` 建唯一索引或按业务主键 upsert；
  - 需要严格一次的下游：以 `event_id` 做 Redis/DB 去重表。
- 全量消息 `event_id = {db}.{table}.snap.{P}.{chunk}.{idx}`（含快照位点 P：同轮重投幂等、跨轮重扫可区分），配合 `phase` 字段，快照重跑不与 binlog 事件混淆（06 §4.1）。

## 3. 投递正确性保障清单

| # | 保障 | 机制（依据） |
|---|------|-------------|
| 1 | 联合主键 DELETE/UPDATE 谓词正确 | 多列谓词 `(pk1,pk2) IN ((?,?),...)`（05 §5.2） |
| 2 | UPDATE 改主键不在目标残留旧行 | before 像检测 PK 变化 → 同事务 delete(old)+upsert(new) |
| 3 | 目标表其他唯一索引不错行折叠 | 启动检测告警 + 文档约束（05 §5.3） |
| 4 | RocketMQ 发送结果可感知 | 同步 SendSync，错误上抛（05 §4） |
| 5 | Kafka 发送结果可感知 | 同步 SendMessage + Return.Successes（05 §3） |
| 6 | sink 失败不推进位点 | 不 ack → 反压 → 位点不动，语义单一（04 §4） |
| 7 | 位点只能由 watermark 推进 | rotate/DDL 强制保存同样校验 flush 结果，无旁路路径（04 §5） |
| 8 | 位点保存失败可见可控 | 重试+告警+超限熔断（03 §5.2） |
| 9 | 全量分块断点续传不丢页 | 表级断点+失败标记（06 §4） |
| 10 | 集群不双写 | leadership 复核 + 位点写 lease 门槛（03 §4.2） |

## 4. 位点推进不变式（实现层的硬规则）

1. 唯一写位点的地方：`PositionPersister`，输入只能是 `Watermark.base` 对应位点——代码层不提供任何「直接保存某位点」的公共入口（人工修位点走 Web `POST /api/v1/position`，confirm=SET-POSITION 门禁 + 审计）。
2. flush 成功（SinkGroup.Send 返回 nil）才 ack；ack 决定 watermark；watermark 决定位点。单向依赖，无环。
3. 位点值附带 `seq` 与 `leader_term`，排障可追溯。

## 5. 故障场景矩阵

| 故障 | MySQL sink 后果 | MQ sink 后果 | 恢复动作 |
|------|----------------|--------------|---------|
| 进程 crash（kill -9） | 重放窗口内事件重复 upsert，终态一致 | 窗口内消息重复 | 自动：从 etcd 位点重启 |
| 优雅停机/发布 | 无重复或极少重复（drain 后保存位点） | 极少重复 | 自动 |
| 目标 MySQL 闪断 | sink 退避重试→熔断暂停→恢复续投 | — | 自动，位点不推进 |
| Kafka/RocketMQ 不可用 | — | 同上；MySQL 侧同步暂停（SinkGroup 全确认语义） | 自动 |
| etcd 抖动 | 位点写重试；选举不受影响（lease 短暂失联会触发让位流程） | 同左 | 自动；连续失败熔断停管线（防重放窗口无限扩大） |
| leader 与 etcd 分区 | 复核失败 → ≤TTL 内停管线；与接任者重叠期重复 upsert | 重叠期重复消息 | 新 leader 接任 |
| 源 MySQL 主从切换 | file:pos 失效 → 启动失败报错；GTID 模式下自动续接 | 同左 | GTID 模式自动；非 GTID 需人工写位点（Web `POST /api/v1/position`） |
| binlog 被清理/位点过期 | 启动检测 PURGED → 拒绝启动并提示 restock | 同左 | 人工触发 restock |

## 6. 暂停的爆炸半径

**必须理解的运行属性**：水位线是全局的（04 §5），**任何一条规则进入 PAUSED（DDL pause、sink 不可重试失败、消息超限）都会让整条管线停止推进位点**——其他表的事件继续被消费、被发送（MQ 侧重复消费无碍），但位点不动。这不是缺陷，而是 no-loss 承诺的必然结果：跳过故障规则的 seq 推进位点 = 永久丢失该规则数据。

工程含义与配套：

| 措施 | 内容 |
|------|------|
| 告警 | `gocdc_pipeline_paused > 0` 为 Critical（11 文档），暂停必须尽快被人工看见/处理 |
| 影响面 | 管线停推 = 全部规则的重放窗口持续增长；恢复后以最大速率追平（受 sink 吞吐限制） |
| 预防 | 不可重试失败大多源于配置/结构漂移——启动结构核对（08 §4）、消息超限预检（05 §7）、DDL 白名单把大部分 poison 拦在运行前 |

## 7. 验证手段（与 14 文档测试策略联动）

- **重放不变式测试**：注入随机 crash 点，断言「位点 ≤ 已投递」恒成立、终态收敛（对账 SQL 比对源/目标）。
- **重复注入测试**：同一批事件重放 N 次，目标表 checksum 不变；MQ 消费端按 event_id 去重后计数=源事件数。
- **混沌测试**：kill leader、断 etcd、断各 sink，观察告警与自动恢复时间（SLO：leader 故障切换 < lease_ttl + 10s；sink 恢复后续投无丢失）。
