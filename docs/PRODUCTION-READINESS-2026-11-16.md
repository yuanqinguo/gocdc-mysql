# gocdc-mysql 生产就绪度评估（2026-11-16）

> 本文不作"代码有没有 bug"的局部判断，而是按**数据正确性 / 可靠性 / 安全 / 可观测 /
> 可运维 / 交付质量 / 容量性能 / 升级回滚 / 合规**九个维度给可上线结论。
> 全部结论基于本仓库代码、文档、CI 配置与历史验证日志；**未在本机真实环境运行**
> （无 Docker），此边界在 §1 明确列出。

## 0. 结论（TL;DR）

| 部署场景 | 结论 |
|---|---|
| 内网、1~3 个源、有运维值守、可接受分钟级暂停 | ⚠️ **有条件可上**——先修 3 个阻断项（§3.1） |
| 公网 / 等保合规 / 多租户 / 7×24 无人值守 | ❌ **不可上**（差距见 §3.4） |
| 依赖无 GTID 的主从切换做容灾 | ❌ **不可用**（切换间隙丢数据不可恢复，项目自身 RUNBOOK 亦如此声明） |

一句话：**工程质量在同类工具中属上游（178 项集成用例历史全绿、RUNBOOK 完备、
水位/租约/DDL 协议严谨），但当前存在 3 个必须先处理的上线阻断项，且缺少
etcd 灾备与容量验证这两个生产必备条件。**

## 2. 九维矩阵

### 2.1 数据正确性 —— 强（含 1 个安全相关缺口）

- **已修复并验证**：位点水位协议、跨会话续扫的丢失安全（globalP 取小）、快照锁
  顺序（P 先于快照）、解锁失败中止、类型归一化（enum 大小写/unsigned zerofill）、
  DDL 字面量默认值等 12 项。
- **缺口**：`三轮-3` 规则编辑器 mask 参数往返丢失——**hash 加盐脱敏会被静默去盐**。
  这是唯一"安全相关"的未修项，且触发路径很短（Web 打开规则编辑器 → 保存）。
- **缺口**：`二轮-2a` ON UPDATE 属性在目标 DDL 中丢失（CDC 路径无数据影响，只有
  目标表被直写时分叉）。
- 历史证据：集成套件 14 组 **178 用例全 PASS**（含 DDL burst、位点回拨、restock、
  多源、HA 切换等场景），说明主链路经过真实 MySQL 验证。

### 2.2 可靠性 / HA —— 良

- leader 选举（etcd lease）+ 位点写租约门槛（防分区双写）+ 失位先停管线 + 优雅
  drain 序列 + 源级失败隔离（D5），设计扎实。
- `/healthz`（liveness）与 `/readyz`（readiness）语义分离正确，避免级联重启。
- **单点**：etcd 集群是唯一协调面（位点/DDL 审批/配置/选主），etcd 全损 = 同步状态
  全丢。**项目未提供 etcd 快照备份/恢复流程文档**（RUNBOOK 10 章无此节）——生产
  必备，属阻断级流程缺口。
- **缺口**：`三轮-1` Web 端口监听失败不退出 → headless 进程，且集群服务级重启编排
  轮询 peer 的 Web `/healthz` 会永久卡住。

### 2.3 安全 —— 弱项，仅适合内网

| 项 | 现状 | 生产要求 |
|---|---|---|
| 管理面鉴权 | HTTP Basic，单账号全权限 | 等保场景需 RBAC/多用户/SSO |
| 管理面传输 | 无 TLS 强制（仅 deploy/README 文字要求反代） | 必须 TLS 反代或内置 TLS |
| 凭据存储 | 前端 sessionStorage（过渡方案），服务端会话未实现 | 应改 HttpOnly 服务端会话 |
| 登录限速 | 已有（20 次/分 → 锁 30s） | ✅ 可接受 |
| **MySQL 源/目标连接** | **DSN 无 TLS 参数——连接不加密**（本次新查证） | 跨网段必须加密或明确隔离 |
| Kafka / RocketMQ | SASL / TLS / ACL 齐备 | ✅ |
| 审计留存 | etcd 环形仅 **100 条** | 合规需外送日志/长期留存 |
| SQL 注入 | 标识符统一反引号转义、参数化绑定 | ✅ 已核查 |

### 2.4 可观测性 —— 良

- 指标 20+（吞吐/延迟三口径/水位/队深/暂停态/全量进度/源就绪），语义清晰。
- 7 条告警规则（leader 缺失、管线暂停、事件延迟、位点写入失败、转换错误、源宕、
  源失败）+ Grafana 看板。
- 结构化日志 + 事件码（Event*）。
- **缺口**：水位洞（worker 卡死前兆）只有日志无告警；无 tracing（可接受）。

### 2.5 可运维性 —— 强

- RUNBOOK 覆盖：日常检查、位点回拨、restock、新增表、主从切换、DDL 挂起、
  etcd 故障、下游迁移、发布前置检查、多源运维、**键迁移回滚**、**升级检查单**、
  **容量规划**。
- Web 控制台提供：源级暂停/恢复、restock、位点迁移（GTID ⇄ file:pos）、DDL 审批、
  配置在线编辑（CAS + 活体预检）、服务级重启编排。
- 本章是该项目最突出的优势之一。

### 2.6 交付质量 / 测试 —— 良（有 2 个流程缺口）

- CI（`.cnb.yml`）：前端 typecheck+lint+test+build、`go build/vet/test -race`、
  **govulncheck 漏洞扫描**、docker build+push。
- **缺口 1：CI 仅在 `tag_push` 触发**——主干提交/PR 没有门禁。
- **缺口 2：CI 不跑集成测试**（`-tags=integration` 缺失）——178 个集成用例只在
  手工 `.verify/v2` 跑过，无法防回归。
- **缺口 3**：无 golangci-lint（`Makefile lint` 目标存在但 CI 未接）。
- 单测覆盖较好（20 包中 18 包有测试，含并发/竞态/边界表驱动）。

### 2.7 容量 / 性能 —— CPU 侧已有基线，端到端压测仍缺

- **（2026-11-16 更新）已补 14 个 CPU 侧基准并实测**（i5-14600KF）：行转换
  1.78 µs（22 allocs）、水位 Ack 49-253 ns（0 alloc）、MQ 消息编码 8.8-12.4 µs、
  500 行×50 列批量 upsert 的 SQL 文本实测 **212 KB**——常规 `max_allowed_packet`
  （≥4MB）下安全，先前的报文超限担忧在常规宽度下不成立（极宽表+大字段仍建议
  启动期预检）。详见 REVIEW 报告附录四。
- RUNBOOK 给了 `GOMEMLIMIT ≈ N × 150MB + 100MB` 的经验值，仍无端到端压测支撑
  （真实吞吐上限需对真实源库压测）。

### 2.8 升级 / 回滚 —— 良

- etcd 键空间 v1→v2 迁移：幂等 CAS + 完成标记 + 失败放行 + RUNBOOK 回滚章节。
- 配置编辑 CAS 防并发覆盖；`apply-restart` 服务级滚动重启（follower 先、leader 后）。
- 无自动化金丝雀/一键回滚（依赖容器编排与配置回退），可接受。

### 2.9 合规 / 数据治理 —— 弱

- 脱敏能力完善（fixed/hash/phone/email/truncate/null + 盐环境变量），但
  **Web 编辑路径会丢参数（三轮-3）**，治理流程不可靠。
- 审计仅 etcd 环形 100 条 + 日志；不满足等保"留存 ≥6 个月"类要求（需外送 SIEM）。
- 无数据主体删除/导出等合规工具（CDC 场景通常由源库承担，可接受）。
- 许可证 Apache-2.0，商用无障碍。

## 3. Go / No-Go 清单

### 3.1 上线阻断项（必须先修，3 项）

1. **`三轮-3` 脱敏参数丢失**——Web 编辑任何规则组后，带参 mask（hash 盐/truncate
   keep/fixed value）被静默降级。最小修法：编辑器检测到带参对象时阻断保存并提示
   改 YAML；完整修法：扩展 `列=算法(参数=值)` 语法双向编解码。
2. **`三轮-1` Web 端口失败不 fail-fast**——headless 会让集群重启编排永久卡住；
   与 metrics 端口口径对齐即可（传 `stop`）。
3. **MySQL 连接加密**——若源/目标跨不可信网段，必须加 DSN `tls` 支持（go-sql-driver
   原生支持，改动小）；若确定全程内网隔离，需把"网络隔离要求"写进部署检查单并由
   运维书面确认。

### 3.2 上线前必须完成（流程/配置，非代码，4 项）

4. **etcd 定时快照备份 + 恢复演练**（当前完全缺失；etcd 全损 = 位点/DDL/配置全丢）。
5. **CI 门禁**：主干/PR 触发 + 集成套件纳入（当前只 tag_push、不跑集成——
   **本次实证了代价**：`-cluster` 默认值回归（R4）在主干潜伏 3 天，首次真实
   跑集成即被抓出；若 CI 有集成门禁，当天就能拦住）。
6. **监控接入落地**：把 7 条告警规则接到实际 Alertmanager，补"水位洞"告警。
7. **binlog 保留策略确认**：保留时长必须 > 最长计划停机 + 故障恢复时间；否则
   PURGED 只能 restock 全量重跑（代价极大）。

> 上线后 30 天项。

### 3.3 上线后 30 天内（9 项）

三轮-2（对账口径）、三轮-4/5/6/7/8/9（前端）、二轮-2a/b、golangci-lint 入 CI、
审计日志外送、压测基线、故障演练（kill leader / 网络分区 / etcd 抖动 / 大表全量）。

### 3.4 明确不可用的场景

- **无 GTID 的跨实例容灾切换**：file:pos 模式切换间隙丢数据不可恢复（项目 RUNBOOK
  自行声明"强烈建议 GTID"）。生产容灾必须 GTID。
- **等保/审计合规环境**：管理面无 RBAC/TLS 强制、审计留存不足。
- **目标端存在非 CDC 直写**：ON UPDATE 丢失、exclude 列 NOT NULL 等约束会导致分叉。
- **超大表单次全量**：无压测数据，全量时长与资源上界未知，需先单表演练。

## 4. 我的判断

**这是一个"设计优秀、验证偏科、运维文档成熟、但交付流程与灾备有缺"的项目。**

- 代码层的核心正确性（位点、快照一致性、DDL 屏障、租约防脑裂）达到了我做过的
  同类 CDC 工具里的上游水平，历史 178 项集成用例全绿也佐证了主链路可靠。
- 但它**不是"下载即上生产"的产品**：CI 只在打 tag 时跑、集成测试不进流水线、
  etcd 灾备空白、容量无基线、管理面安全仅内网级别。
- 决策建议：**内网 + 有值守 + 先完成 §3.1 三项阻断与 §3.2 五项流程准备 → 可以上，
  建议单源灰度 1~2 周再扩源**。这与"直接上生产"是两件事。
