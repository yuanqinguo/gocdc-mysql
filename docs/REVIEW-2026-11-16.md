## 1. 总体评价

这是一套设计水准相当高的 MySQL CDC 实现。核心正确性机制经得起推敲：

- **水位/位点协议**（`pipeline/watermark.go`）：连续水位 + XID/Rotate 锚点，位点恒 ≤ 已投递数据，at-least-once 语义严谨；重复 Ack 幂等、残留锚点均摊清理都处理了。
- **DDL 三策略与 barrier**（`pipeline/worker.go`）：同表分片 FIFO 消除跨 worker 新旧结构竞态；收敛循环解决 DDL 风暴中间态；TRUNCATE 显式镜像；断点续跑幂等（Settled 不重执行）。
- **防脑裂**：位点/标记写全部经 lease 门槛事务（`position/store.go`），leader 在位复核带超时，失位先停管线后更新注册。
- **错误分类**（`sink/errors.go`）：可重试白名单 + 永久错误标记，方向正确（宁可 PAUSED 不盲试）。
- **并发细节**：对象池、槽位 channel 独占连接、CAS 写配置/审计，race 检测干净。

问题集中在**外围与边界**：类型归一化的两个实锤数据缺陷、快照锁的异常路径、一个红着的测试、以及若干工程卫生问题。以下按严重程度列出，每个问题含：位置、原因、复现逻辑、修复建议、影响面。

## P1 — 数据正确性缺陷（实锤，已实测复现）

### P1-1 enum/set 取值被整体小写化，不可逆丢失原始大小写

- **位置**: `internal/schema/normalize.go:20`（`p.base = strings.ToLower(strings.TrimSpace(s))`），取值消费点 `normalize.go:37-38`；下游 `transform/convert.go:509-513`（按索引映射输出）、`convert.go:532-540`（set 位掩码映射）
- **严重度**: 高（行级数据错误，写出到下游的内容错乱）
- **原因**: `parseColumnType` 在解析**之前**对整个 `COLUMN_TYPE` 原文做 `ToLower`，之后再从括号内截取 `inner` 交给 `parseQuotedList`。enum/set 的取值字面量是大小写敏感的数据，被 lower 后不可逆丢失。
- **复现逻辑**（已用临时探针测试实测，输出如下）:
  ```
  IN="enum('New','Done','IN_PROGRESS')"  → vals=[new done in_progress]
  IN="set('A','bB')"                     → vals=[a bb]
  ```
  源表列 `status enum('New','Done')`：binlog 中该列以**索引**承载（如 1），`convEnum` 按 `EnumValues[0]` 输出 → 下游收到 `"new"` 而非 `"New"`。
- **修复建议**: 只对基类型名与尾缀属性做小写：先按首个 `(` 截断，对括号**前**与最后一个 `)` **后**的片段分别 `ToLower`/`TrimSpace`；`inner` 原样传入 `parseQuotedList`。补充回归用例覆盖混合大小写取值。
- **影响面**:
  - MySQL sink：目标列若为同构 enum，MySQL 写入 `'new'` 会按枚举匹配规则落到 `'New'`，**多数情况自愈**；但目标列若是 varchar（常见异构映射），则永久写入小写值。
  - Kafka/RocketMQ sink：消息体直接携带错误大小写字符串，**无自愈路径**，下游消费者拿到的数据与源库不一致。
  - DDL 对账（`sink/mysql/ddlgen.go` 若用 `EnumValues` 生成目标 DDL）：目标表被建成小写取值的 enum，与源库结构分叉。

### P1-2 `unsigned zerofill` 尾缀导致 unsigned 标记彻底丢失

- **位置**: `internal/schema/normalize.go:21-24`（仅识别以 `" unsigned"` **结尾**）、`normalize.go:34-35`（括号解析把 `)` 之后的尾串静默丢弃）；消费点：`transform/convert.go:39`（unsigned → 无符号转换分支）、`stock/scan.go:186-201`（游标绑定）、`stock/marker.go:197`（LastPK 编解码）
- **严重度**: 高（键值解释错误 → 行寻址、游标、断点全部错乱）
- **原因**: `"bigint(20) unsigned zerofill"` 不以 `" unsigned"` 结尾 → 后缀匹配失败 → `unsigned=false`；随后 `p.base[:open]` 只保留 `"bigint"`，`" unsigned zerofill"` 整段被无声丢弃。MySQL 中 `zerofill` 隐含 `unsigned`，此信息一并丢失。
- **复现逻辑**（已实测）:
  ```
  IN="bigint(20) unsigned zerofill"      → unsigned=false
  IN="decimal(10,2) unsigned zerofill"   → unsigned=false
  IN="int unsigned"                      → unsigned=true   （正常路径对照）
  ```
  源表 `id bigint unsigned zerofill` 且存在 `> 2^63` 的主键：binlog 侧该值以回绕的负 int64 到达，`convInt` 因 `Unsigned=false` 走有符号分支 → 负数直接写往目标；全量扫描的 PK 游标比较同样按有符号解释，排序游标错乱。
- **修复建议**: 括号解析完成后，对 `)` 之后的剩余尾串用 `strings.Fields` 逐词判定：遇 `unsigned` 或 `zerofill`（后者隐含置位 unsigned）即 `p.unsigned = true`；其余未知词保留原样（前向兼容）。补回归用例。
- **影响面**: 存量业务库中 `zerofill` 列（报表/订单号类场景不少见）所在表的全量 + 增量数据皆错；错误形态是"静默写错值"而非报错停机，属于最难察觉的一类。

## P2 — 快照/锁的异常路径缺陷

### P2-1 `UNLOCK TABLES` 失败仅打标记，FTWRL 可能被持有整个快照期

- **位置**: `internal/stock/session.go:150-153`
- **严重度**: 高（源库写阻塞的业务事故级操作风险）
- **原因**:
  ```go
  if _, err := conn.ExecContext(ctx, releaseLockSQL(usedMode)); err != nil {
      usedMode += " (unlock_failed)"   // 仅注记，无重试、无中止
  }
  ```
  解锁失败（瞬态网络抖动、连接被掐）后，会话照常建立、扫描照常开始，而 **FLUSH TABLES WITH READ LOCK 仍被持有**——全局读锁直到全量扫描完成（可能数小时）或进程死亡才释放。
- **复现逻辑**: 配置 `stock.lock_mode: ftwrl`（或 auto 探测到 ftwrl），在 `SHOW MASTER STATUS` 与 `UNLOCK TABLES` 之间制造一次连接级错误（如网关掐流、kill 查询）→ 日志出现 `mode=ftwrl (unlock_failed)` → 源库所有写入（INSERT/UPDATE/DDL）持续阻塞。
- **修复建议**: 解锁失败时走 `abort` 路径（放锁重试 + 关闭全部快照连接 + 返回错误，让本轮当选周期重试建立快照），绝不能带着锁进入长扫描；或至少对 `UNLOCK TABLES` 做几次有界重试，仍失败则中止。
- **影响面**: 全量初始化期间的源库写入可用性；auto 模式下凡有 RELOAD 权限的部署都可能走到 ftwrl 路径。

### P2-2 backup/none 锁模式下，位点 P 在快照开启**之后**读取 → 存在静默丢事件窗口

- **位置**: `internal/stock/session.go:117-147`（顺序为：conn0 `START TRANSACTION WITH CONSISTENT SNAPSHOT` → 克隆连接各自开快照 → `SHOW MASTER STATUS` 读 P → 解锁）
- **严重度**: 中高（需要非 ftwrl 模式；但 **auto 模式在无 RELOAD 权限的托管库上会静默回落到 backup**，是现实可达路径）
- **原因**: 设快照视图固定于 T1、P 读取于 T2 > T1。**ftwrl** 下锁窗口内无任何提交，T1 与 T2 之间无增量，协议正确。但 **backup 锁只挡 DDL 不挡 DML**（none 无锁同理）：`(T1, T2]` 间提交的事务既不可见于快照（视图已固定），又被增量起点 P 跳过（P 已包含它们）→ 该窗口内的 DELETE/UPDATE **静默丢失**。`none` 模式配置注释声明了"可能窗口丢失"，`backup` 模式的注释（session.go:19）只说"不锚 DML"，未声明丢数据风险。
- **复现逻辑**: 源库账号无 RELOAD（auto→backup 回落）+ 持续写入负载：在 `START TRANSACTION WITH CONSISTENT SNAPSHOT` 与 `SHOW MASTER STATUS` 之间提交一条 `DELETE FROM t WHERE id=1` → 快照看不到 id=1 的行（已删），增量从 P 开始也不再重放该 DELETE → 目标库 id=1 永久残留。
- **修复建议**（方向性：宁可重复、不可丢失——重复由幂等 upsert 吸收）:
  1. 把 `SHOW MASTER STATUS`（P 读取）移到**快照事务开启之前**：P ≤ 视图位点的部分会被增量重放，重复投递由下游幂等消化；
  2. 或 backup/none 模式下启动日志 + 文档显式声明"不保证不丢变更，生产建议 ftwrl 或授予 RELOAD"；
  3. GTID 模式下 P 的比较建议同步用 GTID 集合包含关系（`mysql.ParseGTIDSet` + `Contain`）替代纯 file:pos 字典序（`laterPos`，session.go:223-231），跨文件场景更稳。
- **影响面**: 显式配置 backup/none 的部署，以及 auto 回落 backup 的无 RELOAD 权限部署；丢失形态静默（无报错、无指标），只能靠核对（verify）事后发现。

### P2-3 连接重拨计数跨整表累计，长扫描 >10 次瞬断即整表失败

- **位置**: `internal/stock/scan.go:80`（`var redials int`）、`scan.go:87-95`（仅递增不归零）、`scan.go:90`（`time.Sleep` 不感知 ctx）
- **严重度**: 中
- **原因**: `redials` 在 `ScanTable` 顶部声明，`maxChunkRedials=10` 是**整表生命周期累计上限**而非滑动窗口。成功取块后计数不归零，公网链路上每隔较长时间被网关掐一次连接的大表，第 11 次断连时 `IsConnLost` 满足但配额耗尽 → 整表 `failed`。另 `time.Sleep(time.Duration(redials)*100ms)` 在 ctx 取消后仍会睡满。
- **复现逻辑**: 公网源库网关按 ~30 分钟流龄强杀连接；一张需 6+ 小时的大表累计断连 11 次 → `stock: %s.%s … 重连` 后 `redials == maxChunkRedials` → 表标记 failed，全量中断待人工 restock。
- **修复建议**: 每次成功 `fetchChunk` 后 `redials = 0`（连续失败语义）；退避改为 `select { case <-ctx.Done(): return …; case <-time.After(…) }`。
- **影响面**: 公网/长距离链路的大表全量成功率；内网低断连环境几乎不触发。

### P2-4 断点续扫协议形同虚设：LastPK 写入但恢复时无条件丢弃

- **位置**: `internal/stock/service.go:86-89`（`StatusRunning` → `lastPK = nil`）；写入侧 `scan.go:139-151`
- **严重度**: 中低（正确性无损——重扫由幂等 upsert 兜底，但协议与实现背离）
- **原因**: 注释称"session_id 匹配才可续扫"，代码却是**无条件** `lastPK = nil`；且 `newSessionID()`（session.go:216-220）每进程随机生成，跨进程重启永不匹配 → 任何中断都整表重扫。`Marker.LastPK/ChunkSeq/RowsDone` 与每块一次的 etcd 进度写入（throttle 节流下仍是高频写）全部白做。
- **复现逻辑**: 大表扫描中途进程被杀 → 重启后 marker 为 running/failed → 整表从 `WHERE (pk) > (…)` 的零游标重扫，先前逐块持久化的进度无人消费。
- **修复建议**: 二选一：(a) 真正实现续扫——恢复时校验 `SessionID` 无法跨进程则改为校验 `SnapshotP` 一致 + LastPK 可解码即续扫；(b) 承认不支持续扫，删除 LastPK 相关字段与逐块进度 etcd 写（保留行数指标），简化协议、消除注释与实现的背离。倾向 (a)：快照位点是重启安全键，比 session 随机 ID 可靠。
- **影响面**: 大表中断恢复成本（重复全量投递）；etcd 写放大；维护者被"支持续扫"的注释误导。

## P3 — 资源与安全

### P3-1 schema 缓存无界增长，无失效机制

- **位置**: `internal/schema/schema.go:104-109`（`load` 只插入不删除，且每次全量复制 map）；`schema.go:102`（`LoadedAt` 写入后全仓无读取方）
- **严重度**: 中（长期运行的 leader 实例）
- **原因**: `snapshot.tables` 与 `versions` 均只增不减；无 `Drop/Invalidate` API；DROP/RENAME 后按旧名 Get 仍命中陈旧条目（依赖 worker 侧 `ErrTableNotFound` 跳过逻辑兜底，但缓存条目本身永不清理）。每次 `load` 复制整个 map，表数多时 O(n) 复制在频繁 DDL 下放大为 O(n²)。
- **复现逻辑**: 分表场景 `orders_202601…` 逐月建新表、DROP 旧表，运行一年 → 缓存 ~12×表数份陈旧条目常驻。
- **修复建议**: 增加 `Drop(schema, table)` / `InvalidateSchema(schema)`，在 DDL 处理 DROP TABLE/RENAME 时调用；或给快照加简单 LRU 上限 + `LoadedAt` TTL 校验（顺带让 `LoadedAt` 有消费者）。
- **影响面**: 内存缓慢泄漏 + DDL 风暴期的复制开销；对表数固定的部署无感。

### P3-2 前端将管理员凭据明文存入 JS 可读 Cookie（7 天）

- **位置**: `web/src/app/session.ts:33-42`（`storeSession`）、`session.ts:11-30`（`readStoredSession`）
- **严重度**: 中（取决于部署边界：内网 + 无 XSS 时风险受控）
- **原因**: 架构上前端需要凭据重组 `Authorization: Basic …` 头（client.ts:31-36），于是把 `{username, password}` 以 URI 编码 JSON 存入非 HttpOnly Cookie，`Max-Age=7d`、`SameSite=Lax`、仅 HTTPS 加 `Secure`。任何 XSS（现在未见注入点，但 antd 渲染的任意后端字符串构成未来风险面）或同浏览器其他被攻破页面均可直接读取管理员口令；管理台具备位点改写、DDL 审批、整集群重启等高危权限。
- **复现逻辑**: 登录后在控制台执行 `document.cookie` → 明文可见 `gocdc_session={"username":"admin","password":"…"}`。
- **修复建议**: 服务端签发随机 session token 的 **HttpOnly** Cookie（服务端保存会话态或签名 token），前端不再持有原始口令；过渡方案至少改 `sessionStorage`（关闭标签即失效）+ 文档强制生产走 TLS 反代。
- **影响面**: 管理台凭据泄露面；`auth_disabled` 匿名形态不受影响（存的是空凭据）。

### P3-3 Web/API 无登录失败限速

- **位置**: `internal/api/auth.go:34-53`（恒时比较正确，但无失败计数/锁定/限速）
- **严重度**: 低中（内网部署可接受）
- **原因**: Basic auth 可被在线暴力破解；`/healthz` 无鉴权属正常，但 API 全部端点共享同一无限速边界。
- **复现逻辑**: 对 `GET /api/v1/status` 以恒定速率遍历口令字典，服务端无任何节流。
- **修复建议**: 进程内简单失败计数（按 IP/全局，滑动窗口锁定），或文档明确要求反代层限速 + TLS。
- **影响面**: 弱口令部署被爆破接管管理台的风险。

### P4-1 Makefile / .gitignore / embed.go 中文注释乱码（双重编码事故残留）

- **位置**: `Makefile:1-4`、`.gitignore` 全部注释、`internal/api/embed.go` `serveIndex` 中的 500 文案（用户可见）
- **严重度**: 低

## 二轮-1（已修复）ddlgen 生成 datetime/timestamp 字面量默认值的非法 SQL

- **原因**: Modal onOk/按钮 onClick 直接返回 `mutateAsync()` 的 promise，antd
  Modal 不消费该返回值；失败时 onError 有 message 提示但 promise 仍 reject。
- **复现**: 确认让位/暂停/恢复时后端 500/409 → message.error 弹出的同时控制台
  `Uncaught (in promise)`。
- **影响面**: 全局错误监控误报崩溃；接入 onunhandledrejection 的环境被误触发。
- **修复建议**: 改 `mutate()`（onError 已在），或 `.catch(() => {})`。

## 三轮-7 [低] 让位入口两视图角色判定不一致

- **位置**: `DashboardPage.tsx:292`（单源视图仅 leader）vs `396/414`（聚合视图
  leader||single）
- **复现**: role=single 时聚合视图可让位，钻入单源视图入口消失。
- **影响面**: 行为矛盾；single 是无选举模式，让位语义本就存疑。
- **修复建议**: 统一判定（建议 leader-only，single 隐藏让位）。

## 三轮-8 [低] 聚合视图暂停确认框 loading 未校验目标源

- **位置**: `DashboardPage.tsx:440`（对照 426 行有正确守卫）
- **复现**: 卡片 A 暂停 pending 时打开卡片 B 确认框 → B 假 loading 且被禁用。
- **修复建议**: `loading: pausePipeline.isPending && pausePipeline.variables === pauseSid`。

## 三轮-9 [低] currentSid 失效落入无法自愈的错误页

## 实测过程发现并修复 2 个新问题

### R4 [高] 零参数引导被 `-cluster` 默认值短路（存量回归，修复）

- **位置**: `cmd/gocdc/main.go:63`（commit 333deb1，11-13 引入）
- **现象**: 首跑 A7（下游不可达失败隔离）FAIL，桩日志
  `cluster="verify" 与 -cluster flag="edu.mall.gocdc" 不一致` 拒启。
- **根因**: 333deb1 把 `-cluster` 默认值从 `""` 改为 `config.ServerFullName`。
  flag 包无法区分「显式传参」与「默认值」，非空默认值把 bootstrap.go:109 的
  仲裁链（flag > 引导文件 > gocdc-mysql）**恒短路**——所有零参数引导桩的
  cluster 恒为 edu.mall.gocdc，与正文 cluster=verify 冲突即 fatal；env 模式下
  协调面前缀也悄然偏离文档约定的 `/gocdc/gocdc-mysql`（bootstrap.go:95）。
- **证据**: 历史全绿日志 v2-g10.out 是 11-02 生成（早于该提交）；此后 CI 不跑
  集成，回归潜伏 3 天无人发现——**这正是就绪度报告指出的 CI 流程缺口的直接代价**。
- **修复**: 默认值还原 `""`（缺省语义本就由仲裁链承担，flag 帮助文本与之一致）。
  首跑在 A7 止损中止（每个死桩烧 40s 超时，全组尽是同根因），修复后重跑。

### R5 [低] 套件锁被 rmqcons 消费者继承，尾窗内连环拒启（修复）

- **位置**: `65_mq.sh` 等 4 个脚本的后台 spawn
- **现象**: 首轮全量跑完 11 组全绿后，70_adv/80_exceptions/90_hiprio 三组瞬间
  被拒：「另一个 v2 验证脚本正在运行（/tmp/v2/.lock 被占）」。
- **根因**: lib.sh 用 `exec 9>/tmp/v2/.lock; flock -n 9` 做组间互斥，gocdcbin 桩
  已打 `9>&-` 补丁（注释注明"节点不继承 flock fd——活多久锁被占多久"），但
  rmqcons 消费者（`-idle 15s` 尾窗存活）的 spawn 漏了同款处理——组脚本退出后
  锁仍被消费者持有整个 idle 窗口，下一组恰在窗口内启动即被拒。
- **修复**: 4 处 rmqcons spawn + launch_workload.sh 补 `9>&-`（与既有补丁同款）。
  补跑三组全过。
